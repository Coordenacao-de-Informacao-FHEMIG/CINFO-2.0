Apresentação Estratégica

PROJETO CINFO 2.0

Não são apenas novos BIs. É uma nova forma de trabalhar com a informação.

O que houve?

Dia 05/05: Consultas da CINFO derrubam o ambiente FHEPROD.

Este incidente gerou o acionamento imediato da GTIC e da Phillips, evidenciando uma fragilidade crítica em nosso fluxo atual.

Qual é a situação?

  • A CINFO atua em um ambiente hospitalar crítico (Sistemas ERP/Tasy) que não permite impactos de performance.
  • Crescimento acelerado do BI: BE, Leitos, FF e Descentralização.
  • Exigência de agilidade, confiabilidade e escalabilidade.
Problema Central: Como evoluir o BI sem travar o Tasy e sem tornar a manutenção insustentável?

Termos Técnicos

Atualmente não temos Staging (camadas intermediárias).

Como está:
ERP (FHEPROD) → Power BI ❌
Como deve ser:
ERP → STAGING → Power BI ✅

Como trabalhamos hoje?

Arquitetura de Dados - Phillips/GTIC

  • 3 bancos OLTP: FHEPROD (Real), FHEHOM (Dump Março), FHETRN (Dump Março).
  • Ausência de ODS (Operational Data Store): não temos camada analítica intermediária dedicada (staging)
  • Staging:tabelas derivadas e estruturadas para análise, abastecidas a partir do ERP
Metáfora: Imagine tentar contar todos os grãos de feijão no estoque de um restaurante enquanto os chefs estão tentando cozinhar. Você atrapalha a cozinha (Produção) e demora mais para contar (Análise).

Consequências:

  • Uso de banco de produção (OLTP) para fins analíticos (OLAP).
  • Sobrecarga: O Tasy foi feito para transações rápidas (inserir/atualizar), não para varrer milhões de linhas ou cruzar tabelas gigantes.
  • Risco de lentidão ou indisponibilidade do sistema hospitalar.
  • O problema não é a existência dos BIs — é que eles estão ligados no banco errado.

Processos CINFO

  • Consultas diretas e pesadas no FHEPROD: queries complexas importadas pro BI.
  • Regras de negócio não documentadas e espalhadas: muitas queries, transformações, colunas personalizadas e medidas DAX diferentes.
  • Alterações diretas em arquivos PBIX publicadas manualmente no servidor 95.
    • Hoje não aproveitamos todos as inovações disponíveis do Microsoft Fabric Pro nem todos os recursos de otimização dentro do Power BI.

    Consequências:

    • Uso de banco de produção (OLTP) para fins analíticos (OLAP).
    • Sobrecarga do ERP assistencial e risco direto à operação hospitalar
    • Opacidade dos cálculos e agregações, dificultando a auditoria e correção dos resultados em tela.
    • Baixa reutilização dos dados importados e alto custo de manutenção (refreshs constantes e lentos).
    • Dificuldade no versionamento dos PBIX com risco de sobreposição de trabalho.
    • Impossibilidade de desenvolvimento colaborativo: "cada hora um trabalha".

Como deveríamos trabalhar?

Arquitetura (Phillips)

Curto-Médio Prazo: Staging / ODS

  • Criação de tabelas físicas derivadas voltadas ao consumo analítico: "sub-banco" intermediário no FHEPROD (metatabelas: censo, produção profissional, contas).
  • Dados extraídos das tabelas fato do FHEPROD com atualização períodica e incremental em metatabelas (extração controlada de madrugada via ETL: procedure, job, event, etc.),
  • Podem ter transformações leves (JOIN, CASE, FLAGS).
  • Melhora significativa na performance.

Médio-Longo Prazo: Data Warehouse

  • Modelo modelado para análise (Fatos e Dimensões).

Coordenação de Informação (CINFO)

A revolução se baseia em 5 princípios:

  1. Proteção absoluta do banco de produção.
  2. Separação de responsabilidades (Dados x Métricas).
  3. Arquitetura em camadas.
  4. Reutilização corporativa.
  5. Atualização incremental.

Novas Ferramentas

PBI DataFlows

Processamento em segundos via Query Folding.

GitHub (BI as Code)

Uso de .pbir, controle de versão, histórico de quem mudou e o quê.

GitHub Branches

Desenvolvimento simultâneo (main, develop, features) sem conflitos.

GitHub Actions

Pipeline automatizado. Publicação segura após aprovação.
